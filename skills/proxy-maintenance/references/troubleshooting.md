# 分层排查

## 入口与状态

先记录症状、最近一次变更、当前配置／模式／接管状态与目标错误。能从现场确定的不重复问用户。诊断保持只读；不要先清 DNS、换节点或重启使证据消失。

| 表现 | 最小区分检查 |
|---|---|
| 切订阅后断网 | 当前 UID／配置、扩展绑定、provider 成员、链式引用、解析错误与内核是否仍运行旧配置 |
| 显式代理正常但 TUN 失败 | 同目标解析结果、目的地址、实际命中与 TUN 路由，先排除两次请求选了不同地址 |
| 入口可达但固定链失败／407 | 逐级代理引用、最终代理认证／有效期／来源限制，不自动重置凭据 |
| 所有路径都慢 | 本地链路、并发任务、VPS CPU／可用内存／I/O，再看网络对照 |
| 某协议或某地址失败 | 客户端实际拨号地址、服务监听、云与主机规则、TCP／UDP 差异 |
| 请求失败且 REJECT 命中 | 可能是预期保护；用时间与命中增量确认，不把它修成裸直连 |
| 应用打开后空白或连不上，其他软件正常 | 进程参数是否带固定入口、防火墙拒绝记录；不带入口启动被拒属于预期，见 [应用断线保护](../../proxy-setup/references/macos-app-firewall.md)，不把规则放宽为全部允许 |
| 应用自动更新失败 | 更新器是否不认代理参数而被防火墙拒绝；改为手动更新，不临时放行直连 |

## 地址、协议和线路对照

先确认监听、认证、证书和规则正确，再按必要分支选择：
- 同一协议、同一服务器对比已授权的不同入口地址；入口不可达不等于服务器不可用。新增 Reserved IP 等云资源是变更，不是只读排查。
- 同一入口对比 SS 与 Hysteria2 等受支持协议，保持目标和最终出口不变。TCP 重传、窗口和 RTT 是线索，不能仅凭累计计数算精确丢包率。
- 对比仅 VPS 与再经最终代理，判断慢发生在哪一段。机场更快不直接证明有 CN 优化；ICMP 丢包也不等于业务丢包。
- 只有证据指向相应瓶颈才调整拥塞控制、MTU、带宽参数或套餐。Hysteria2 不是永远更快，TCP 也不是对某个网站天然更好。

用户态 SS／HY2 代理由进程重新建立连接，不能因 Linux `ip_forward=0` 就判定其不可用；路由型 VPN 则另查转发、路由与 NAT。不把两种架构混为一谈。

性能方法见下文 [性能对照](#性能对照)。同目标连续两次失败先停下：指出哪条假设被证伪、哪个决定引入问题、能否同时满足要求、是否旧问题换形式；结构性冲突不能靠继续调参解决。

## 服务与资源

服务单元名可能不等于实际进程名；结合监听 PID、进程、配置路径和服务管理器定位，不凭一个猜测的 systemd 单元 inactive 就宣布服务停止。日志与命令行只提取必要字段，避免密码。

CPU、load、I/O wait 用短时采样判断；内存看 available、进程 RSS 与缓存，磁盘是持久存储，不能替代进程所需 RAM。没有资源耗尽证据不建议升配或添加 swap，也不强杀正在推进的系统更新。

## 修复后

修改持久源并通过受支持入口生成和加载，再读回运行配置。控制 API 的临时加载不代表下次启动仍有效；路径被安全机制拒绝时不扩大安全目录绕过。只观察本次相关连接，旧连接不默认强行断开。

交付已证实原因或剩余疑点、改动范围、真实对照结果与回退方式。测试足够区分原因即停止；长期监控另按用户要求安排。

## 性能对照

- 区分即时流量曲线、延迟、建连时间与吞吐；空闲时几 KB/s 不代表带宽上限。
- 同目标、相近时间、相同下载量和并发，区分冷连接与复用；只改一个变量，必要时交错重复一次。
- 下载设置响应体、流量和超时上限；优先小样本，未能区分原因时再扩大，不做无限压力测试。报告 MB/s 与 Mbps 时明确换算口径。
- 固定出口对照使用隔离客户端或独立 loopback 入站，不切生产组、不启用第二套抢路由的 TUN；核对测试进程自身是否仍被生产 TUN 接管。
- 分别看设备→VPS、设备→VPS→最终代理、机场路径。更换入口、协议和最终出口同时进行的对比不能定位单一原因。
- 短测不证明全天稳定；供应商快或网站“优化入口”的宣传不证明代理数据链路有 CN2／CMI／专线优化。
