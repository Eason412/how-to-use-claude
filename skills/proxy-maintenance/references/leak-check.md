# DNS 与 WebRTC 泄露验证

## 判定口径

系统登记的 DNS 地址不等于实际查询出口。DNS 地址与网页出口不同、解析器有多个 IP 或位于另一地区，也不能单独证明泄露。判据是受保护查询是否绕过预期路径；节点引导解析与网站解析分开检查。面向非技术用户先说“有没有绕过代理”，再给必要证据。

区分三层证据：配置表达的意图、运行态实际路径、测试观察到的行为。正常态通过不覆盖节点失效、入口关闭、内核退出或系统重启。WebRTC 出现 VPS 地址应区分出口不一致与真实接入网地址暴露。

## 现场检查

- macOS 用 `scutil --dns`、`scutil --proxy`、路由和接口状态建立基线；用 `networksetup -getdnsservers` 与 DHCP DNS 对照区分显式设置与自动下发。不要先清缓存／重启破坏证据。
- 通过用户实际使用的浏览器运行检测页；远程工具的出口不能代替用户电脑。结合代理控制器的测试目标连接和本机 socket，核对入站、规则与 chain。
- 定向抓包同时观察物理接口与 TUN，接口从现场发现。用新随机测试域名分别测试 UDP／TCP DNS；记录过滤条件、捕获窗口和丢包。只有 TUN 中看到发往某 DNS 的包，不证明它已经从物理网卡发出。
- 端口 53 抓包不覆盖 DoH／DoT 或全部 WebRTC 端口。加密 DNS 结合上游地址与连接链判断；STUN 按实际测试服务器和端口观察，不能把某个固定端口零包当成所有 UDP 都无泄露。
- WebRTC 用候选收集结果、错误及网络证据交叉验证。无候选或 `No Leak` 不能单独归因某条拒绝规则。自建本地测试要确认代码完成、接收端正向自检有效，再观察是否收到浏览器探测；默认不申请摄像头／麦克风权限。
- IPv6 查实际地址、路由与连接；关闭 AAAA 不证明无字面 IPv6 旁路。`::ffff:` 的 IPv4 映射结果不能充当真正 IPv6 出站测试。

## 工具与失败解释

[webrtc/samples](https://github.com/webrtc/samples) 的 Trickle ICE、[tcpdump](https://github.com/the-tcpdump-group/tcpdump) 与 [macvk/dnsleaktest](https://github.com/macvk/dnsleaktest) 各自提供不同证据。使用下载脚本前检查实际代码与外部依赖；命令行结果不能替代具有独立代理策略的浏览器。

fake-IP 模式下，基于 ping 的脚本可能只得到合成地址而未触发外部递归解析。后端无结果、解析异常、测试未完成都不能计为通过；先查探测机制，不盲目换 DNS。无法获取抓包权限就说明缺少哪层证据，密码由用户在本机输入。

报告只保留必要的脱敏结果和有权限限制的本地产物；清理临时监听与脚本运行进程。需修复或故障关闭时使用 [应用故障保护](../../proxy-setup/references/egress-app-protection.md)，不要默认把检查升级为全机防火墙改造。
